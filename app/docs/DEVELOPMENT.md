# 开发实录 · 观点进化缸

> 用途：记录本项目开发过程中的关键技术决策、踩坑与解法，供复赛迭代与后来者参考。
> 撰写时间：2026-09-13（48 小时冲刺首夜，接入真实凭证后更新）

## 0. 今晚最大的发现：隐藏接口 `question_answers`

**这是本项目最重要的一段开发经验：文档会过时，额度清单才是能力地图。**

1. **起因**：接入 Access Secret 后跑通全部接口，发现真实额度结构与官方文档严重不符（直答 2 次/日而非 100，热榜 2 次/日而非 100）。
2. **线索**：调用免费不耗额度的 `/api/v1/quota`，返回的 `APIID` 清单里出现了一个文档从未提到的 `question_answers`（知乎问题回答，10 次/日）——**有额度项就必然有对应端点**。
3. **探测**：盲猜路径 `/api/v1/content/question_answers`，传 `QuestionID` 返回 `10001: QuestionUrl must be a valid Zhihu question URL`——错误信息直接告诉了我们正确参数名。传 `QuestionUrl=<知乎问题链接>` → 200，返回该问题下真实回答列表。
4. **收尾**：该接口字段极简（`ContentToken/Url/Summary` + `Paging{IsEnd,NextOffset}`），无赞同数。用同题知乎搜索做 **LCS≥20 连续汉字匹配**富化——搜索摘要其实是查询偏置的中段片段（前缀匹配 0 命中，实测教训），只有 LCS 能可靠判定"同一回答"（785 赞同精确归属，不同问题的相似回答会被正确拒绝）。
5. **结果**：原方案"输入问题链接抓取该问题下的回答"从不可行变为**已实现**，产品核心体验升级为真实问题直取。

方法论沉淀：**错误信息是最好的文档；quota 清单是隐藏能力地图；免费接口可以随便探。**

## 1. 可行性审查如何改变了产品形态

原方案（`../docs/观点进化缸-项目文档.md`）设想"输入问题链接抓取全部回答 + 真实历史时间轴 + 折叠化石层"。逐项对照知乎开放平台 API 后发现三个根基性缺口：

| 缺口 | 原假设 | API 现实 | 解法（最终状态） |
|---|---|---|---|
| 无"问题→回答列表"接口 | 抓取该问题下所有回答 | 文档内仅有 `zhihu_search` 关键词搜索（≤10 条/次） | **已解决**：实测发现隐藏端点 `question_answers`（URL 直取），叠加搜索 LCS 富化形成双通道 |
| 无历史时序数据 | 拖动时间轴看任意一天 | 所有字段只有当前时点值 + EditTime | EditTime 升序重演"入场"，UI/报告双标注"AI 演化重建 · 非历史记录" |
| 无折叠/删除数据 | 化石层 | 完全不可得 | 整体移除，不做任何虚假声称 |

**经验**：黑客松选题先审数据可得性再定功能边界；"标注推演"（明确声明）与"伪装真实"（评审一戳就破）之间必须选前者。

## 2. API 集成要点（以实测为准）

- **鉴权**：`Authorization: Bearer <secret>` + `X-Request-Timestamp`（秒级），缺一不可。
- **真实额度以 `/api/v1/quota` 实测为准，不要信文档**：本项目账号实测为直答 2/日、热榜 2/日、搜索 10/日、问题回答 10/日、用户数据 1000/日、知识库 500/日。文档写的是"邀测"通用额度（搜索 5000/日等），校园季试用凭证额度小一个到三个数量级。
- **429 不消耗额度**（实测两次 429 后 `TotalUsed` 不变），但 200 + 解析失败会消耗——所以标注只重试一次以下，宁缺毋滥。
- **直答 JSON 输出**：LLM 输出常被 ```json 围栏或前后杂文污染。实现 `extractJson()`：剥围栏 → 定位首个 `[{` → 括号配平提取（含字符串/转义态扫描）→ `JSON.parse`。比"正则去掉围栏"健壮得多。
- **标注批量化**：10 条回答一次 `zhida-fast-1p5` 调用完成（prompt 内以 `n` 序号对齐返回），而不是每条一次。
- **双层额度守卫**：本地计数 + `zhidaRemaining()`（quota 接口免费，结果缓存 60s）。本地守卫误判好过现场 429。
- **缓存分层（额度防泄漏五道闸）**：
  1. 结果缓存：热榜 12h（2 次/日只够早晚各一次）；生态缸 24h 按问题名+URL 哈希；搜索 6h；question_answers 6h；放生分析 1h（问题+草稿哈希）；
  2. **并发去重**：`dedup(key, fn)` 保证同 key 并发请求只发一次上游调用（实测 3 个并发仅 1 次构建，全部返回同一结果）——双击/前端重试不再双倍消耗；
  3. **磁盘持久化**：生态缸缓存写入 `server/data/eco-cache.json`，服务重启不丢已消耗额度换来的数据（当天多次重启的实测教训）；
  4. 双层直答守卫：本地计数 + `zhidaRemaining()`（quota 接口免费，结果缓存 60s）；
  5. stale-while-error：热榜耗尽时官方返回**空列表而非报错**——必须显式判空并降级为演示热榜+警告横幅，否则前端白屏。
- **搜索相关性**：`zhihu_search` 返回的是"相关内容"而非"同题回答"，用查询词与标题的字符 2-gram 重现率过滤（阈值 0.25），不足 3 条时放宽取 Top 6——宁可样本少，不要跑题的"物种"。
- **跨接口同一回答判定**：`question_answers` 与 `zhihu_search` 的内容 ID 完全不同域（实测 token 匹配 0 命中）；搜索摘要是查询偏置的中段片段（前缀匹配 0 命中）。最终用 **LCS≥20 连续汉字** 判定，实测精确命中且能拒绝不同问题的相似回答。

## 3. 前端技术决策

- **d3-force 而非手写力导向**：`不重复造轮子` 原则下直接用官方力模拟；**同步跑 300 tick 取终态**而非逐帧动画——生态图是"重算后呈现"的分析视图，不是粒子玩具，同步布局让时间轴拖动与参数切换零延迟。
- **自绘 SVG 报告而非 html2canvas**：报告 SVG 全部由代码生成（无外部图片/字体），序列化 → Image → canvas → PNG 全程同源，规避 html2canvas 的跨域污染与样式还原度问题，且产物在知乎侧清晰可读。
- **能量模型**：圆面积 ∝ 能量（`r = 18 + 46·√(energy/max)`），环境干预四参数（推荐权重/时近度/情绪气候/大V加权）纯前端重算，`computeEnergy()` 单函数可解释。

## 4. 生存概率模型

`P = 100 × (0.35×策略蓝海度 + 0.25×立场差异化 + 0.20×权威压力缓冲 + 0.20×互动基础度)`，与直答 thinking 的预测按 **AI:规则 = 6:4** 混合。设计理由：
- 直答可能在额度耗尽/网络故障时不可用 → 规则模型兜底，功能永不中断；
- 纯 LLM 概率不可复现、不可解释 → 规则部分公式公开写进 UI，评委可验证；
- 直答失败时自动 `rule-only` 模式并在报告中标注来源，不冒充 AI 结果。

## 5. 踩坑记录（环境与工具链）

1. **沙箱 shell 的 stdout 吞噬**：本机 PowerShell 工具对原生命令的 stdout 经常返回空（`Write-Output` 也可能被吞），但文件写入可靠。**解法**：所有需要"看结果"的验证一律落盘再 Read（`e2e-test.cjs` 用 fetch 请求 + `writeFileSync` 写结果文件）。
2. **npm.cmd 被 cmd.exe 包装**：PowerShell 工具禁止 cmd.exe，`npm.cmd` 直接调用被安全拦截。**解法**：用 node 直接跑 `node_modules/npm/bin/npm-cli.js`。
3. **默认 registry 超时**：外网 registry 在本环境 ETIMEDOUT（280s 不够）。**解法**：`--registry=https://registry.npmmirror.com` + 后台运行 + `run-npm.cjs` 诊断器（spawnSync 输出落盘，绕开 PowerShell 流包装）。
4. **PowerShell `*>` 重定向污染日志**：原生命令 stderr 会被 PS 5.1 包成 NativeCommandError 记录，日志里混入"所在位置 行:445"等伪内容。**解法**：一律用子进程语言（node）自己的文件 IO，不用 shell 重定向收集诊断。
5. **Port 冲突/进程清理**：dev 用 `node --watch`，注意 Windows 下后台 task 停止后端口释放有延迟，重跑前先 `netstat` 确认 8787/5173。
